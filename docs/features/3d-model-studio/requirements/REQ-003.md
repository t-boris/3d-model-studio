## Statement

In v1, support conversational creation of new 3D geometry and iterative conversational refinement of new and imported models, including explicit dimensional constraints. The app documents supported wording for dimensional targets with units, such as “final span along X is 30 mm.” The app locally extracts each explicitly requested target from the user's wording. If an explicitly requested dimension cannot be extracted unambiguously, the app asks the user to restate that dimension using the documented wording. The app explicitly reports unsupported dimensional constraints. The app may apply an AI creation or revision only after it has extracted every explicitly requested dimension and verified that the proposed geometry meets every extracted target within the documented numerical tolerance. By default, an explicit dimension applies only to the operation that sets it. Users can explicitly pin a dimension on a new or imported model to preserve it across subsequent manual and AI edits until they change or unpin it.

## Acceptance Criteria

- [x] Users can provide explicit dimensions and units when requesting geometry creation or revision.
- [x] The app documents supported wording for specifying a dimension and its unit, including “final span along X is 30 mm.”
- [x] The app locally extracts each explicitly requested dimensional target and its unit from the user's wording.
- [x] If the app cannot unambiguously extract an explicitly requested dimension, it asks the user to restate that dimension using the documented wording.
- [x] The app explicitly reports unsupported dimensional constraints.
- [x] The app blocks application of an AI proposal while any explicitly requested dimension remains unresolved, even when the proposal matches the agent's interpretation.
- [x] Before applying a creation or revision operation, the app verifies that the proposed geometry meets every locally extracted target within the documented numerical tolerance.
- [x] After the user restates an unresolved dimension using documented wording, a proposal outside the documented tolerance for any locally extracted target is rejected, and a proposal within tolerance for every target passes the requested-dimension check.
- [x] An explicit dimension applies only to the operation that sets it by default.
- [x] Users have explicit controls to pin and unpin dimensions on new and imported models and can change a pinned dimension.
- [x] A pinned dimension remains in force until the user changes or unpins it.
- [x] Before applying each subsequent manual or AI edit, the app checks the proposed geometry against every pinned dimension using the same documented numerical tolerance used for requested dimensions.
- [x] If a proposed manual or AI edit violates a pinned dimension, the app rejects the edit and identifies the conflicting dimension.

## I-3 implementation evidence

The active model retains explicit pins across operations and receives requested lengths as arguments to each proposal. The workspace exposes Pin Current, Change Pin and Unpin for new and imported meshes. Tests/run-dimension-checks.sh exercises both origins.

## Conversation contract

A clarification continues the same request with its description and prior answers. The studio reviews the proposed surface and the requested width, depth and height with their explicit units. Applying an accepted edit uses the shared model transaction. An unsupported dimensional constraint, a provider error or an invalid proposal leaves the active geometry intact.

## I-6 implementation evidence

Commit 04a8e98 connects provider questions and geometry proposals to a native preview and the shared transaction. Tests/run-provider-checks.sh exercised a clarified creation and further revisions for all three routes, plus repeated revisions of all three imports. It checked current-operation targets, pin conflicts at preview and Apply, stale proposals, malformed geometry, provider failures and unsupported constraints. Rejection preserved the active mesh. ## Current plan I-2 evidence

The shared workspace transaction checks the current pins for direct edits, numerical span changes and offline conversational proposals. Tests verified that one-time spans expire and that pins can be added, changed and removed on new and imported geometry. A change retains the entered unit. The native app set height to 10 mm and then 9 mm with Set Once, changed the pinned height using centimeters, and removed the pin. Local conversational wording and restatement acceptance is tracked in I-3.

## Current plan I-3

Commit e741b23 documents final spans in the modeling sheet and provider guide. Each operation tracks the user's statements and clarification answers locally. Tests/run-provider-checks.sh offered a candidate that satisfied its provider assessment while two equal-valued user requests lacked axes. Proposal construction blocked it, and the session retained the description, shape answer and prior restatements. After clarification, independent X, Y and Z misses of 0.0101 mm were rejected. A candidate at the inclusive ±0.01 mm endpoints on all three axes passed. A later revision accepted a fresh local height despite a conflicting provider value. New blocks and STL, OBJ and Core 3MF imports passed repeated scripted edits on each route. Current pins were rechecked at Apply.

## I-3 verified behavior

On all three scripted routes, a clarified creation and repeated revisions of new, STL, OBJ and Core 3MF blocks passed. A candidate matching the provider assessment remained blocked with unresolved targets. After restatement, each 0.0101 mm miss identified its axis, and a candidate at the inclusive ±0.01 mm endpoints committed. Unsupported measurements produced an error. A pin added during review rejected the edit and preserved the revised mesh. Commit 9d57ffa also covers a unitless answer to a direct height question. An intervening width restatement leaves height pending, then an explicit Z span resumes the request with both local targets.
