## Context

F-006 identifies an undefined geometry access boundary in REQ-006 for Codex, Claude, and Antigravity. An imported model may contain confidential geometry outside the faces selected for an edit.

## Alternatives

1. Limit selection edits to the selected faces and their boundary geometry. If more context is needed, ask the user to change the selection or switch to a whole-model edit.
2. Give the agent access to the entire active model, including geometry outside the selection, after obtaining user consent. The selection identifies the edit target.

## Decision

In v1, apply the same geometry access rules to Codex, Claude, and Antigravity. For model creation, the agent receives the user's description and the geometry of the model being created. For whole-model edits, the agent may access the entire active model. For selection edits, the agent initially receives only the selected faces and geometry along their boundary. Before granting access to any additional parts of the model, the application identifies those parts, explains why they are needed, and asks the user to approve access for the current operation.

## Reason

Selection edits expose only the geometry available by default for the task. Operation-specific approval lets users provide broader context when it is needed while retaining control over which additional parts the agent receives.

## Consequences

Update REQ-006 with acceptance criteria for all three workflows and all three integrations. For selection edits, verify that additional geometry is withheld until the user approves the specific parts requested, and that approval expires when the operation ends. If the user declines, the agent continues with the available geometry or explains why it cannot proceed. Permission to access additional geometry does not expand the authorized edit boundary, which is tracked separately in F-005 under REQ-005.

## Implementation evidence

Tests/run-provider-checks.sh exercised the production request boundary for each of the three provider routes. From a three-face mesh, only face 0 and its three vertices were initially serialized. The request for context across its shared edge resolved locally to face 1 with a reason. Approval added only face 1 and its referenced vertex, preserving face 0 as the edit target and withholding disconnected face 2. Declining sent no follow-up. A new operation withheld face 1 again. Unknown IDs, unrelated edges, empty reasons, expired review tokens and a late reply after provider switching were rejected. UI and live service verification remain pending.

## Current plan I-4 status

Implemented in a62f502. The disclosure panel uses the 3MF occurrence mapping to name requested parts and lists only the face IDs covered by that approval. It displays a source object name when available and distinguishes repeated objects by build item and component path. Offline captures on all three routes verified that an explicit sibling face and a boundary neighbor were withheld until approval, that a later withheld face stayed private after refusal, and that a new operation reset access. Occurrence labels and the assembly map stay local.
